The customer flow currently relies on local setup data and simulated persistence. The API now provides public endpoints for the real customer path, but one contract gap remains for multi-staff tips: `businessId`.

## Goals / Non-Goals

**Goals:**

- Load real touch-page business, touch point, and staff data from the public API.
- Create and confirm single-staff tips through the API.
- Record skip-tip events through the API.
- Submit customer reviews through the API.
- Track Google/Yelp review clicks through the API.
- Support multi-staff tips when a public `businessId` source is available.
- Keep API details inside repositories and hooks.

**Non-Goals:**

- Do not call Merchant-auth endpoints from the anonymous customer QR flow.
- Do not expose raw staff payment account information from touch-page data.
- Do not implement actual payment confirmation from Cash App/Venmo/Zelle/PayPal.
- Do not add new state libraries.

## Decisions

### D1 - Anonymous customer APIs use repository methods with `anonymous: true`

**Decision:** All `PublicTouch`, `PublicBusinesses`, and `PublicTips` calls go through a new public-touch repository and pass `{ anonymous: true }` to `httpClient`.

**Rationale:** Customer QR flows are guest-facing. The HTTP client must not attach stale Merchant or Staff bearer tokens to public endpoints.

### D2 - Query params belong in `httpClient`

**Decision:** Add first-class `params` support to the HTTP client rather than constructing query strings in components.

**Rationale:** Existing repositories already call `client.get(path, { params })`, and customer endpoints require query params for `sessionId`, `staffId`, `method`, and `amount`.

### D3 - `businessId` must come from a public source

**Decision:** The frontend must not use `GET /api/v1/merchant/business` to obtain `businessId` for the customer QR flow. The correct source is the public touch response or another public endpoint.

**Rationale:** `GET /api/v1/merchant/business` requires Merchant auth. Customer QR flows are anonymous. Using the Merchant endpoint would break for real customers and leak role assumptions into the public flow.

**Preferred backend update:**

```json
{
  "business": {
    "id": "guid",
    "slug": "bitcoin-nail-bar",
    "name": "Bitcoin Nail Bar",
    "logoUrl": "https://...",
    "description": "Premium nail salon..."
  }
}
```

### D4 - PaymentMethod enum mapping is isolated in the repository

**Decision:** UI steps use stable method names (`CashApp`, `Venmo`, `Zelle`, `PayPal`, `AppleCash`). `publicTouchRepository` maps those names to the backend wire format.

**Rationale:** The PDF describes `PaymentMethod` as integer enum values, while Swagger currently exposes it as string enum values. Centralizing mapping keeps any backend correction localized.

### D5 - Review destinations must be public, but not necessarily complete business settings

**Decision:** The public flow may consume safe review destination fields (`googleReviewUrl`, `yelpUrl`, `facebookUrl`, `feedbackEmail`) if backend adds them to the public touch page. It must not fetch full Merchant business settings.

**Rationale:** High ratings require Google/Yelp routing. Low ratings may use private feedback email. The Merchant endpoint has those fields, but it is authenticated.

### D6 - Multi-staff tips are feature-gated until `businessId` exists

**Decision:** Implement multi-staff repository/hook surfaces, but the UI should show an intentional unavailable state if `touchPage.business.id` is absent.

**Rationale:** The endpoint requires `businessId` and `businessPaymentMethodId`. A clean frontend implementation cannot fabricate or privately fetch the business id.

## API Contract Summary

### Single-staff tip

```http
GET  /api/v1/touch/{businessSlug}/{touchPointSlug}?sessionId={uuid}
GET  /api/v1/touch/payment-link?staffId={id}&method={PaymentMethod}&amount={amount}
POST /api/v1/touch/tip
POST /api/v1/touch/tip/{tipId}/confirm
POST /api/v1/touch/review
```

### Skip-tip review-only

```http
GET  /api/v1/touch/{businessSlug}/{touchPointSlug}?sessionId={uuid}
POST /api/v1/touch/tip/skip
POST /api/v1/touch/review
```

### Multi-staff tip

```http
GET   /api/v1/touch/{businessSlug}/{touchPointSlug}?sessionId={uuid}
GET   /api/v1/public/businesses/{businessId}/payment-methods
POST  /api/v1/tips/multi-staff
PATCH /api/v1/tips/{tipId}/confirm
POST  /api/v1/touch/review
```

## Risks / Trade-offs

**[Risk] Missing `businessId` blocks multi-staff tips.**

Mitigation: implement repository/hook contracts and gate the UI until backend adds `business.id` to the public touch payload or provides an equivalent public lookup.

**[Risk] PaymentMethod enum mismatch.**

Mitigation: repository-level mapping; prefer Swagger string enum unless runtime testing proves integer enum is required.

**[Risk] Public review links are missing.**

Mitigation: keep review submit working; show external review buttons only when public links exist.

**[Risk] Public business payment methods expose `accountInfo`.**

This is expected for business payment methods used in multi-staff tips. It must not be confused with staff payment account privacy; staff raw `accountInfo` stays hidden behind `payment-link`.
